# Step 62 — Alert Remediation Guidance

Step 62 adds deterministic, non-mutating guidance to alert history.

## Scope

An alert now has a guidance layer that answers **what the user can safely investigate next** without executing remediation.

Guidance is generated by the Rust `health-status` crate through `guide_alert()` and exposed to the Desktop application through the `alert_guidance` Tauri command. The Desktop Alert History view renders the guidance alongside the existing explanation, performance evidence, and Step 61 process contributors.

## Safety boundary

Step 62 does not authorize or execute system changes. Guidance may recommend normal user-controlled actions such as closing an application through its ordinary controls, but Linux Powerhouse does not perform those actions from this feature.

The guidance explicitly distinguishes observations from causation and adds verification-first language for critical events. Snoozed and dismissed warnings receive persistence/recheck guidance rather than being treated as resolved.

## Architecture

```text
Alert Event
    ↓
Performance Evidence
    ↓
Process Evidence (CPU / Memory)
    ↓
Deterministic Alert Guidance
    ↓
Desktop Alert History
    ↓
User decides what to do
```

No automatic remediation path is introduced by Step 62.

## Acceptance criteria

- [x] Deterministic guidance exists for CPU, memory, swap, storage, and network alerts.
- [x] Critical alerts prioritize verification.
- [x] Snoozed/dismissed warnings encourage rechecking persistence.
- [x] Guidance is exposed through a Tauri command rather than duplicated in React.
- [x] Alert History renders guidance with existing alert evidence.
- [x] Guidance explicitly states that no system changes are performed.
- [x] Guidance does not claim process causation.
- [x] No alert policy, snooze, dismissal, persistence, or remediation behavior is changed.
